The Vector Dispatch Unit (`rvv_backend_dispatch`) is responsible for receiving micro-operations (uops) from the upstream uop queue, resolving data and structural hazards, and issuing these uops to the appropriate functional unit Reservation Stations (RS) along with the necessary operand data.

## 1. Architectural Function

The dispatch unit serves as the instruction issue and operand fetch stage for the Vector Backend. Its primary responsibilities are:

1.  **Uop Ingress**: Dequeue uops from the frontend uop queue.
2.  **Hazard Detection**: Analyze source/destination registers against in-flight instructions to detect Read-After-Write (RAW) data hazards and structural limitations (e.g., VRF read port availability).
3.  **Operand Assembly**: Fetch operands from the Vector Register File (VRF) or bypass them directly from the Reorder Buffer (ROB) if the data is generated by an older, unretired instruction.
4.  **Issue**: Dispatch the assembled uop, complete with its operand data and ROB entry tag, to the target Reservation Station (ALU, PMT/RDT, MUL, DIV, FMA, or LSU) and allocate an entry in the ROB.

## 3. Hazard Resolution Logic

The dispatch unit employs a sophisticated hazard resolution network to maintain throughput and correctness.

### Read-After-Write (RAW) Hazards

Data dependencies are checked at two levels:

1.  **Uop vs. ROB (`raw_uop_rob`)**: Source operands (`vs1`, `vs2`, `vd` acting as a source, and mask `v0`) of the incoming uop are compared against the destination registers of all in-flight instructions currently residing in the ROB. If a match is found, the dispatch unit evaluates if the data is available for bypassing.
2.  **Uop vs. Uop (`raw_uop_uop`)**: Because multiple uops may be dispatched in a single cycle (`NUM_DP_UOP`), the dispatch unit checks for dependencies between concurrent uops. For example, if uop `i` writes to `vd`, and uop `i+1` reads from that same `vd`, a stall is generated.

When a RAW hazard is detected against the ROB, the unit either:

- **Forwards Data**: If the older instruction has completed execution and its result is in the ROB (`rob_byp`), the data is bypassed directly to the RS, avoiding a VRF read.
- **Stalls**: If the older instruction has not yet produced the result, the dispatch pipeline stalls until the data is available.

### Structural Hazards

The primary structural hazard evaluated during dispatch is the limitation on VRF read ports. The `rvv_backend_dispatch_structure_hazard` module dynamically calculates if the combination of concurrent uops requires more read ports than the Vector Register File (VRF) physically provides (`vr_limit`). If the limit is exceeded, dispatch is stalled. The logic is parameterized based on the dispatch width.

#### VRF Read Port Capacity Limits

The structural hazard tracker supports two dispatch configurations, statically scaling the VRF read port bounds to match the pipeline width.

- **`DISPATCH3` Configuration**: In a 3-uop dispatch configuration, the VRF exposes **6 physical read ports**. The ports are statically routed to serve up to 3 parallel uops (`uop0`, `uop1`, `uop2`):

  - **rd0**: `uop0.vs1` or `uop2`
  - **rd1**: `uop0.vs2` or `uop2`
  - **rd2**: `uop0.vd` / `vs3` or `uop2`
  - **rd3**: `uop1.vs1` or `uop2`
  - **rd4**: `uop1.vs2` or `uop2`
  - **rd5**: `uop1.vd` / `vs3` or `uop2`

- **`DISPATCH2` Configuration**: In a 2-uop dispatch configuration, the VRF exposes **4 physical read ports** to serve `uop0` and `uop1`:
  - **rd0**: `uop0.vs2` / `uop0.vs1` / `uop0.vd`
  - **rd1**: `uop0.vs1` / `uop1.vd`
  - **rd2**: `uop1.vs2` / `uop1.vs1` / `uop1.vd`
  - **rd3**: `uop1.vs1` / `uop0.vd`

#### Structural Hazard Stall Generation

The vector dispatcher evaluates the `uop_class` of all concurrently dispatching instructions (e.g., `VVV`, `XVV`, `XVX`, `VXX`, `XXV`, `XXX`, `VVX`) to determine total port demand. If the requested vectors across all active uops exceed the physical port capacity, the dispatcher asserts `arch_hazard.vr_limit = 1'b1`, stalling dispatch until a valid structural permutation is available.

- **Stall Conditions (DISPATCH2)**: The following `uop_class` combinations across `{uop0, uop1}` will definitively trigger a structural stall (`vr_limit = 1'b1`):

  - `{VVV, VVV}`
  - `{VVV, XVV}`
  - `{VVV, VVX}`
  - `{XVV, VVV}`
  - `{VVX, VVV}`

- **Stall Conditions (DISPATCH3)**: Complex routing multiplexers attempt to map `uop2` into any unused ports left by `uop0` and `uop1`. If no valid permutation exists (e.g., all 3 uops are `VVV`), the `vr_limit` stall is asserted.

## 4. Operand Bypassing and Byte Type Analysis

To support mixed-width operations and precise masking, the dispatch unit tracks detailed byte-level type information (`UOP_OPN_BYTE_TYPE_t`).

- **Bypass Multiplexing**: The `rvv_backend_dispatch_bypass` module selects the final source operand data from either the direct VRF read (`vrf_byp`) or the ROB bypass network (`rob_byp`).
- **Tail/Inactive Elements**: The dispatch unit applies agnostic rules (`vta`, `vma`) to unmodified elements based on the active vector length and mask.
