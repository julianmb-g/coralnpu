This document details the software synchronization primitives and the Command
Ring Buffer architecture used to orchestrate data movement and execution on the
CoralNPU.

## Command Ring Buffers

The CoralNPU IP does not implement a dedicated hardware-managed Command Ring
Buffer exposed directly to the external host via AXI4. Instead, command
orchestration and execution queues are managed in software and utilizing the
internal hardware queues (such as the `u_command_queue` in the RVV backend) and
the DMA Engine.

External hosts offload complex execution sequences by writing chained DMA
descriptors to system memory. This effectively forms a software-managed Command
Ring Buffer.

- The host writes execution descriptors into a ring buffer in shared memory.
- The host updates the `DESC_ADDR` CSR in the DMA Engine and sets the `start`
  bit in the `CTRL` register.
- The NPU's DMA Engine asynchronously fetches and executes these descriptors.
- The host monitors the `STATUS` register (polling for the `done` flag) or the
  `XFER_REMAIN` register to synchronize with the NPU's progress.

For detailed descriptor memory layouts, register-level CSR specs, circular ring
buffer algorithms, status polling mechanisms, and complete C programming
examples, see the dedicated
[Command Ring Buffer & Execution Queue](command_ring.md) documentation.

## Synchronization Primitives

The CoralNPU scalar core and instruction decode pipeline enforce strict
serialization and interlocks to maintain synchronization between instruction
execution and memory accesses.

### Fences and Memory Barriers

The instruction pipeline implements hardware interlocks for synchronization
instructions (`fence`, `fencei`).

- **Slot 0 Exclusivity**: Fence instructions are flagged as `forceSlot0Only()`,
  meaning they must execute exclusively in the first pipeline slot. No other
  instructions will dispatch in the same cycle.
- **Pipeline Interlock**: Fence instructions stall dispatch as long as memory
  or the Load/Store Unit (LSU) remains active (`mactive || lsuActive`). This
  ensures all prior memory transactions complete before subsequent instructions
  are fetched or executed.

### Interrupts and Polling

- **Wait for Interrupt (`WFI`)**: The `WFI` instruction halts the core execution
  and clock-gates the NPU until an asynchronous interrupt is received (`irqn`
  active-low signal).
- **CSR Interrupt Configuration**: Software can enable and monitor interrupts
  via standard RISC-V Machine-Mode CSRs, specifically the `mie` (Machine
  Interrupt Enable) and `mip` (Machine Interrupt Pending) registers at addresses
  `0x304` and `0x344`.
- **Status Polling**: For peripherals like the DMA Engine that do not generate
  interrupts (in the v1 implementation), synchronization must be achieved by
  software polling the respective `STATUS` register.
